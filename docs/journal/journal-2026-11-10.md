# Journal 2026-11-10

## M12: Puzzle only (T95–T100)

M12 removed the playtest set, face tiles, Classic, Endless and the mode axis,
and replaced ozterisk's name, fonts, palette and brand motion with neutral
placeholders. Puzzle is the only run.

### Decisions made during execution

- **The share heading** is `9dle — …` / `구들 — …`, with no "Puzzle" word.
  T99 deleted the mode group, every run is Puzzle, and T108 rewrites both share
  texts. T100's task file asked for `9dle Puzzle — …`.
- **`GameState.table`** is `PuzzleTable | null`, null only on the title, as
  `docs/spec/architecture.md` gives it. The compiler therefore still asks for a
  null check where a phase-typed state would not.
- **Endless-only tests** went in T98, one task before Endless's code went in
  T99, so the capacity meter had no tests of its own for one commit.
- **Two colour tokens** that nothing uses, `--verm-400` and `--surface-table`,
  stay until M16 replaces the palette, because T100 keeps every colour token
  name.

### Found and deliberately not fixed

- **Old ozterisk issue numbers** (`#31` to `#159`) stay in `src` and `e2e`
  comments. The M12 exit gate forbids the word "ozterisk" there, so they cannot
  be qualified as ozterisk's. A reader may take them for 9dle issues.
- **For M16's restyle and geometry suite:**
  - `--font-ui` lists Gothic A1 before the system stack. In Korean, digits
    render in Gothic A1 if its Korean subset carries them; this was not
    checked.
  - CSS asks for weights 500 and 600, while Hangul loads 400 and 700, so the
    browser substitutes the nearest face.
  - `@container app (width >= 304px)` in `GameScreen.module.css` no longer has
    a stated derivation.
  - The two `>= 5` floors in `e2e/accessibility.spec.ts` are weak checks.
  - Comments in the FeedbackPanel, OverflowControls, LanguageToggle,
    AnswerSlots and Tile styles still cite the old palette's ratios, gold and
    ceramic.
  - `.ringJade` and `.ringGold` draw the same blue. They are decoration; the
    tier's text carries the state.
- **Generic discard code:** the reducer's multi-mark discard,
  `TileInventory`'s capacity sizing and their excess-2 tests remain, though
  Puzzle's excess is always 1. `useGameKeyboard`'s
  `pendingDiscards.length >= required` return and `SUBMIT_INCORRECT`'s null
  check cannot be reached.

### Evidence

- **Network check** on the built preview (`vite preview`): a run played in
  English, then Korean, with Gothic A1 400 and 700 loaded, made 7 requests and
  none to another origin. The same script, given a deliberate cross-origin
  fetch, reported it, so it can catch one.

## M13: Daily tables (T101–T103)

M13 numbers tables by the player's local date (launch day is #1), adds the
offline picker and its generator, and ships 365 tables in
`src/game/dailyTables.json`, with the review file `scripts/daily/review.md`
beside it.

### Decisions made during execution

- **Type-checking `scripts/`** uses its own `tsconfig.scripts.json`, with
  bundler resolution. T102 asked for `"scripts"` in `tsconfig.node.json`, but
  that config's `nodenext` resolution rejects `src/game`'s imports, which have
  no extensions.
- **The compact table format** lives in `src/game/dailyFormat.ts`, which both
  the game and the generator use. T102's generator first wrote the full
  in-memory tables, not the compact format T103 specified.
- **A veto must name an existing table:** an integer from 1 to the list's
  length. Anything else stops the generator before it writes, so a mistyped
  veto is never recorded as done.
- **The bundle check moves to T106.** Nothing in the UI imports the daily list
  yet, so the build cannot show that the tables ship, or that the picker stays
  out. T106's task file now carries the check.

### Found, for Ori

- **Every Daily has par 7.** A table has 8 rows, the band needs par of at
  least 7, and a Daily must need a sacrifice, which costs a row. So par is
  always exactly 7, and every Daily share reads "/ 7".

### Evidence

- **Generator:** 0.65 ms per plant and 2 candidates per 1,000 plants; the full
  run tried 132,753 plants in 90.2 s for 365 tables.
- **The shipped list:** the test re-solves all 365 tables through the same
  unpack the game uses. A reviewer regenerated `review.md` from the list and
  it matched the committed file exactly.

## M14: Daily resume (T104–T105)

M14 rebuilds a Daily from its saved moves, through the real reducer
(`src/game/replay.ts`), and stores today's record on the device
(`src/services/dailyStorage.ts`, key `ndle.daily`). Nothing in the App uses
either yet; M15 wires them.

### Decisions made during execution

- **One move step:** `replay.ts` also exports `applyMove`. The test fixtures
  play moves partway through a run, which a replay from the start cannot do,
  so both use this one step.
- **Unknown fields in a stored record** are dropped, not rejected. The
  record is rebuilt from its validated fields only.

### Found, for M15

- **The tile-id test was blind.** A replay that ignored the id factory still
  passed it, because the first three rows spend the whole opening hand, so no
  live id can collide. The test now cuts after one move, and T107's two id
  tests are rewritten the same way.
- **Record only accepted moves.** A record that fails to replay restarts the
  day, which loses progress and grants a second attempt. T107 should save a
  move only when the reducer accepts it.
- **One submit step:** App's submit and the replay's submit are two copies.
  M15 should share one, so the replay cannot drift from live play.
- **A stored outcome is not checked** against the replayed state. Only a
  hand-edited record can make them disagree; T107 may treat that as corrupt.

### Evidence

- A reviewer replayed all 365 shipped tables. Every par line round-trips
  through storage and replays to par; all 3,285 prefixes replay; all 1,984
  records cut before a discard land in overflow; and dispatching a replay's
  actions from the title gives the replay's state.

## M15: Daily and Practice (T106–T108)

M15 puts the Daily in front of the player: the title offers today's Daily
and Practice, a Daily is one attempt that resumes after a reload or Back,
and each mode has its own game over and share text.

### Decisions made during execution

- **Back sits in the app's top bar**, beside the language toggle, not in a
  row inside the game and game-over screens. A row inside the screens made
  the game 41 px too tall for 393 × 660. It is still the first focusable
  element on those screens. The bar is centered, so Back and the toggle sit
  side by side in the middle; M16's layout decides the final placement.
  `ui-i18n.md` §1.12 and `product.md` §1.10 now say so.
- **A move is saved only when the reducer accepts it.** The handler runs the
  pure reducer first and records only a new state, so a record always
  replays.
- **One attempt even without storage.** When storage is blocked or a save
  fails, the in-memory record for today wins, so Back then Daily neither
  restarts nor rewinds the day.
- **The game-over screen reads its mode from its stats** (`kind`, `number`)
  rather than from a second prop that could disagree with them.
- **App and the replay share one submit step.**

### Found, for M16

- The next-table line reuses the R hint's class; the Daily number is read
  before the verdict heading.
- A Daily left by Back between its last submit and Next Round is labelled
  `Daily #n`, not `Today's result`, until it is opened.

### Evidence

- A reviewer measured the Daily game over and the title in headless
  Chromium at 393 × 660 and 375 × 660, in English and Korean: both fit, and
  Back is 46 px tall. The same check at 393 × 400 reported the overflow, so
  it can fail.
- The built bundle carries the table data and none of the offline picker's
  text.
